# HacXLerate Digital Risk Protection requirements

## Source and scope

The official public HacXLerate page describes Challenge 03 as: “Build an AI-powered Social & App Monitoring platform that helps brands detect fake profiles, impersonation, scam accounts and suspicious mobile apps.” It does not publish a detailed technical brief, required integrations, evaluation dataset, accuracy threshold, or acceptance checklist. This document maps only that verified summary to the current prototype; any additional criterion supplied inside the hackathon platform must be added when available.

Source: [HacXLerate 2026 — Challenges, Challenge 03](https://events.bytexl.com/hacxlerate)

## Known challenge gaps

- Apple lookup uses the public official metadata endpoint with no credentials, but this environment did not make a live request. Google Play metadata and independent app reputation sources are blocked by missing authorized provider access.
- Social evidence is submission-driven unless an authorized provider is injected into the documented connector seam. No platform implementation or credentials are configured here, and the app does not continuously monitor social platforms.
- The monitoring scheduler is opt-in and in-process. Lifespan re-entry within one application instance reuses one scheduler task, and an atomic database claim prevents concurrent checks for one target. Configure one scheduler-enabled worker for predictable operation across the deployment. Checks are sequential and batch-bounded; a process restart recovers from persisted `next_check_at`, while an interrupted claim becomes eligible for recovery after five minutes.
- Screenshot text extraction is wired to real Tesseract OCR through the optional Python `ocr` extra plus an operator-installed Tesseract executable. The effective Python runtime has Pillow, but `pytesseract` and the Tesseract executable are missing. Deterministic tests verify decoding and the downstream API/persistence path using injected OCR/vision fixtures, but do not establish real OCR quality or real Claude vision behavior. No visual/logo similarity implementation is available, so the system makes no such claim.
- Brave Search uses the documented web-search API endpoint and subscription-token header, with a bounded request timeout and at most ten results. It stores only provider result metadata/snippets; no result URL is requested by the server. The configuration is present but the environment has no key, so live availability, account quota and provider terms configuration remain unverified.
- Tavily and Exa use their official JSON search APIs through the same discovery connector contract; exactly one provider is selected by `SEARCH_PROVIDER`. Their deterministic HTTP adapter tests do not make billable/live calls. No Tavily or Exa credentials are configured or exposed by diagnostics.
- No authorized social platform provider is configured, so social monitoring checks persist `unavailable` and do not mark targets active. DNS/RDAP remain governed by the existing opt-in evidence resolver settings; redirects remain disabled by default. Apple lookup is implemented, but no live request was made in this verification.
- Evidence absence is recorded only for complete provider snapshots. Provider failures/partial checks mark old evidence unverifiable in that check result and do not clear it or create disappearance alerts.
- No challenge-specific accuracy threshold, model benchmark, required data source, deployment format, or judge rubric is publicly stated on the linked challenge page. The README's internal benchmark is synthetic/offline and is not evidence of live threat-detection accuracy.

## Final integration verification boundary

- Monitoring API registration, UI delivery, alert acknowledgement, the frontend's create-case action, and copying a persisted monitoring check/alert into a retrieved case snapshot are covered by offline API integration tests. The fixture provider in that test is a deterministic test double; it is not a live discovery result.
- The complete Alembic chain through revision `0006` was applied to a disposable SQLite database after inserting a pre-existing brand row; the row remained and all monitoring tables were present. PostgreSQL offline DDL generation also succeeded.
- The configured driver is PostgreSQL, but a bounded read-only connection probe failed with `OperationalError`. No migration was run against that configured database. PostgreSQL server compatibility and preservation of its existing production data therefore remain unverified.
- Frontend target, alert, and runtime requests render independent error states when one endpoint fails; JavaScript syntax is checked with Node. The repository has no configured frontend package/build manifest, so no frontend bundler build is available.
